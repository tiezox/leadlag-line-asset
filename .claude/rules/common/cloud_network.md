# クラウドで Web を見られないときは、設定を疑う

クラウドで動く Claude Code(claude.ai/code や、デスクトップアプリで Cloud を選んだセッション)がつなげるサイトは、その環境の「ネットワークアクセス」の設定で決まる。設定は「なし」「制限付き」「フル」の3つで、新しい環境は「制限付き」で始まる。「制限付き」では、許可した一部のサイト(GitHub とパッケージの配布元など)にしかつながらない。

ページを開けなかったときは、次のようにする。

1. 「Web にはアクセスできない」と思い込まない。これは設定の問題で、Claude が Web を見られないわけではない。
2. 開けなかったサイトと、出たエラーの文を、そのままユーザーに伝え、「クラウド環境のネットワークアクセスをフルにしてください」と一言頼む。ユーザーが「クラウド環境を編集」の画面で「ネットワークアクセス」を「フル」にして「変更を保存」を押せば、Web を見られるようになる。
3. 開けないまま作業を先へ進めたり、検索結果の要約で確認に代えたりしない。新しい環境を作る申請など、別の設定や回り道を自分で試さない。
4. ユーザーが設定を変えたら、同じページをもう一度試し、開けたことを確かめてから先へ進む。

設定で断られているときの出方: `curl` は `CONNECT tunnel failed, response 403`、WebFetch は `getaddrinfo ENOTFOUND <サイト名>` になる。断られたときの返事には `x-deny-reason: host_not_allowed` が付く。Web の検索は断られているときも使えるので、検索だけができてページを開けないときは、この設定を疑う。WebFetch は、フルにした後も失敗したことがあるので、WebFetch が失敗しても `curl` で開けるかを必ず試す。

なぜ: 261114 に、note-writing のクラウドのセッションで、出典のページを `curl` と WebFetch のどちらでも開けなかった。Claude は「このセッションは通信が許可されていない」と思い込み、ユーザーに確かめないまま、接続先を足した環境を新しく作る申請を出し(サービス側で拒否された)、出典を確かめないまま作業を進めた。実際は、環境のネットワークアクセスが「制限付き」で、許可する接続先が空だっただけだった。
