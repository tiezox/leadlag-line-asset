# SEC のページは、連絡先を名乗って開く

SEC(米国証券取引委員会)のサイトのページをプログラム(`curl` など)で取りに行くときは、道具の名前と連絡先を名乗る。`www.sec.gov` は、名乗りが無いと 403 で断る(ページの題名が「Your Request Originates from an Undeclared Automated Tool」になる)。名乗りは SEC が公式に求めているやり方である(SEC のページ「Accessing EDGAR Data」)。

- 連絡先はユーザーの Gmail アドレスで、環境変数 `GMAIL_ADDRESS` に入っている(261115 にユーザーが許可)。PC では WSL の `~/.profile`、クラウドのセッションではクラウド環境「Default」の環境変数にある。
- 開き方: `curl -L -A "<リポジトリ名> $GMAIL_ADDRESS" <URL>`。SEC のページは別の場所へ移されることがあるので `-L` を付ける。
- アドレスそのものは、コマンドにも、ファイルにも、報告にも書かない。値を表示しない。
- ブラウザのふりをする名乗りは使わない。
- Codex の走行で使うには、そのリポジトリの GitHub Secrets に `GMAIL_ADDRESS` を登録し、ワークフローから Codex に渡す(note-writing では済んでいる)。
- 「自動」モード(操作の前に、別の AI が中身を見て危ないものを止める仕組み)で動くセッションでは、アドレスを外のサイトへ送る操作として止められる(止めた決まりの名前は「Data Exfiltration」)。止められたら、回り道をせず、ユーザーにチャットで「www.sec.gov への curl の名乗りに GMAIL_ADDRESS を入れて送ってよい」と送ってもらい、それから同じ操作をやり直す。公式の説明(「Configure auto mode」)では、ユーザーが操作を名指しして許可すると通る。ただし、この一文で通ることは、まだ確かめていない。クラウドのセッションには、この例外を前もって登録しておく場所が無い(`~/.claude/settings.json` はセッションごとに作り直され、リポジトリの中の設定は読まれない)。

なぜ: 261115 に、連絡先を名乗らずに開いて 403 で断られた。名乗りを付けると、PC、クラウドのセッション、note-writing の Codex の走行のどれでも 200 で開けることを確かめた。クラウドの Claude は、この方法が note-writing の `docs/ノウハウ集.md` にしか書かれていなかったので読まずに試し、403 で止まった。どのリポジトリのセッションでも必ず目に入るよう、共通ルールに置く。同じ日に、「自動」モードで動いたクラウドのセッションでは、このルールどおりに開こうとして止められた。
